# Техническое задание для Codex
## Поэтапная реализация сайта Ксении Богатовой по концепции v5.0

**Версия ТЗ:** 1.0  
**Дата:** 2 сентября 2026 года  
**Проект:** одностраничный сайт финансового директора на аутсорсе  
**Рабочий домен:** `bogatova-cfo.ru`  
**Статус:** мастер-спецификация для разработки, проверки и публикации

---

# 0. Назначение документа

Это ТЗ передаётся Codex как единый источник требований к поэтапной реализации сайта v5.0.

Codex должен:

1. изучить текущий HTML-прототип;
2. сохранить утверждённую визуальную основу первого экрана;
3. устранить технический долг исходного файла;
4. реализовать восемь смысловых блоков v5.0;
5. создать единый квалификационный сценарий обращения;
6. подготовить безопасную событийную аналитику без передачи текста мини-брифа;
7. обеспечить адаптивность, доступность, производительность, SEO и безопасную публикацию;
8. выполнять работу последовательно, с отдельной приёмкой каждого этапа.

Это не задание на самостоятельную переработку маркетинговой концепции. Codex реализует утверждённую логику и тексты, а не придумывает новую услугу, позиционирование, доказательства или обещания.

# 1. Исходные материалы и приоритет требований

## 1.1. Обязательные исходные файлы

Codex должен найти и прочитать:

1. `Концепция_сайта_Ксении_Богатовой_v5.0.md` — утверждённая коммерческая, содержательная, визуальная и техническая концепция.
2. `index(2).html` либо соответствующий ему текущий `index.html` в репозитории — визуальный и технический прототип первого экрана.
3. Реальные локальные материалы в папке `assets`, если они уже существуют в репозитории.

## 1.2. Иерархия источников истины

При противоречии использовать следующий приоритет:

1. последнее прямое решение Ксении в текущей задаче;
2. настоящее ТЗ;
3. концепция v5.0;
4. текущий HTML — только как визуальная и техническая база;
5. концепция v4.0 и более старые документы — только как история, но не как источник для возврата отвергнутых решений.

## 1.3. Правило неизвестных данных

Если для реализации не хватает контакта, реквизита, юридического текста, доказательства, изображения или проверенной цифры:

- не выдумывать значение;
- не брать значение из случайного старого файла без прямого подтверждения;
- не создавать правдоподобную замену;
- использовать технический маркер вида `{{MAX_URL}}`, `{{EMAIL}}`, `{{INN}}` только в разработке;
- внести блокер в `docs/content-blockers.md`;
- не считать публикационный этап завершённым, пока маркер не заменён реальным значением.

## 1.4. Запрет на самостоятельную редактуру

Без отдельного согласования Codex не должен:

- менять H1;
- менять смысловую иерархию «финансовый директор → результат → система → автоматизация»;
- сокращать или расширять утверждённые обещания;
- добавлять гарантии роста прибыли;
- менять цены;
- публиковать непроверенные проценты;
- придумывать отзывы, логотипы клиентов, кейсы, цифры или сроки;
- превращать сайт в сайт интегратора 1С, бухгалтера или разработчика;
- добавлять отдельные услуги, тарифы, лид-магниты или формы захвата;
- использовать формулировки «хаос», «вы теряете миллионы», «автоматизация под ключ», «гарантированный рост», «автоматизирую всё»;
- использовать пазл или головоломку как главную метафору;
- показывать вымышленные дашборды как доказательство результата.

# 2. Режим работы Codex

## 2.1. Работа только по этапам

Codex выполняет только тот этап, который прямо указан Ксенией.

После завершения этапа Codex обязан остановиться. Переход к следующему этапу — только после отдельной команды Ксении.

Запрещено незаметно реализовывать последующие секции «заодно», даже если они технически связаны.

## 2.2. Перед первым изменением

Codex должен:

1. прочитать исходные файлы полностью;
2. проверить `git status`, если проект находится в Git;
3. зафиксировать исходное состояние отдельным коммитом или убедиться, что оно уже сохранено;
4. проверить наличие всех файлов, на которые ссылается HTML;
5. составить список отсутствующих материалов;
6. не изменять изображения и клиентские материалы без необходимости.

Если репозиторий не использует Git, сохранить исходный прототип вне публичной директории, например:

`docs/archive/index-v4-prototype.html`.

## 2.3. Отчёт после каждого этапа

Codex возвращает:

1. **Что выполнено.**
2. **Какие файлы изменены.**
3. **Какие утверждённые требования реализованы.**
4. **Какие проверки выполнены и с каким результатом.**
5. **Какие входные материалы ещё отсутствуют.**
6. **Что Ксении нужно проверить визуально.**
7. **Что намеренно не делалось, потому что относится к следующему этапу.**

Нельзя писать только «готово» без перечня фактических изменений и проверок.

## 2.4. Правило минимального диффа

На каждом этапе менять только необходимую часть проекта.

Исключение — Этап 0, где разрешён системный рефакторинг структуры CSS и JavaScript, потому что в текущем прототипе одни и те же селекторы первого экрана переопределяются повторно. Нельзя продолжать наращивать третий слой переопределений.

## 2.5. Коммиты

Если Git доступен, каждый принятый этап должен завершаться отдельным коммитом. Рекомендуемый формат:

```text
site-v5: stage 0 baseline refactor
site-v5: stage 1 header and hero
site-v5: stage 2 qualifier flow
site-v5: stage 3 early proof and questions
site-v5: stage 4 management cycle
site-v5: stage 5 results and cases
site-v5: stage 6 routes and pricing
site-v5: stage 7 trust video faq
site-v5: stage 8 analytics and attribution
site-v5: stage 9 publication qa
```

Не объединять все изменения в один непрозрачный коммит.

# 3. Коммерческая задача и критерий успеха

## 3.1. Основная задача сайта

Сайт должен переводить подходящего собственника бизнеса по маршруту:

> **квалифицированное обращение → первая встреча → диагностическая карта → платный маршрут → договор.**

Сайт не должен оптимизироваться под максимальное количество любых сообщений.

## 3.2. Главная конверсия

> **Содержательное обращение собственника через MAX после короткого квалификационного мини-брифа.**

Электронная почта — альтернативный канал.

## 3.3. Единый смысловой CTA

На всех ключевых экранах:

> **Разобрать финансовую ситуацию**

В компактной кнопке шапки допустимо:

> **Разобрать**

Фраза «Написать в MAX» не используется как главное обещание. Она допустима только как техническое пояснение после заполнения мини-брифа.

## 3.4. Главные показатели

Сайт должен позволять оценивать:

- начало и завершение мини-брифа;
- содержательные обращения;
- долю целевых обращений;
- первую встречу;
- диагностическую карту;
- платное предложение;
- договор и оплату;
- источник договора;
- часы бесплатного пресейла на один договор.

Офлайн-стадии не реализуются внутри сайта как CRM, но схема событий и источник обращения должны позволять связать сайт с внешним реестром.

# 5. Технологическая архитектура

## 5.1. Стек

- HTML5;
- CSS3;
- vanilla JavaScript;
- локальные изображения, SVG и видео;
- без React, Vue, Angular, jQuery и иных библиотек;
- без внешних UI-компонентов;
- без package manager и обязательного build-step;
- без CDN-шрифтов;
- без внешних иконок;
- иконки — inline SVG либо собственные локальные SVG.

## 5.2. Рекомендуемая структура репозитория

```text
/

│   │   └── icons/
```

Если структура существующего репозитория иная, Codex может адаптировать размещение, но обязан сохранить:

- отдельный HTML;
- отдельный CSS;
- отдельный основной JS;
- отдельный адаптер аналитики;
- централизованную конфигурацию контактов;
- локальные активы;
- отсутствие сборки.

## 5.3. Почему стили и скрипты выносятся из HTML

Текущий прототип содержит встроенные стили, встроенный JavaScript и повторные переопределения одних и тех же селекторов. Для полной страницы это создаст неконтролируемый каскад и потребует небезопасных директив CSP `unsafe-inline`.

На Этапе 0 необходимо:

- вынести CSS в `assets/css/site.css`;
- вынести JS в `assets/js/site.js`;
- создать `assets/js/config.js`;
- удалить дублирующие правила, сохранив итоговый вид;
- не менять композицию первого экрана в рамках технического рефакторинга.

## 5.4. Конфигурация

`assets/js/config.js` должен содержать только публичные параметры:

```js
window.SITE_CONFIG = Object.freeze({
  environment: 'development',
  siteUrl: 'https://bogatova-cfo.ru',
  maxUrl: '{{MAX_URL}}',
  maxPrefillUrlTemplate: '',
  email: '{{EMAIL}}',
  analytics: Object.freeze({
    mode: 'disabled',
    provider: 'disabled',
    counterId: ''
  })
});
```

Правила:

- не хранить секреты;
- не хранить пользовательские данные;
- публикационная проверка должна находить незаменённые маркеры;
- `environment` перед публикацией меняется на `production`;
- при `analytics.mode = 'disabled'` не выполняются сторонние сетевые запросы.

# 6. Семантическая карта страницы

```text
header.site-header
  nav.site-nav
main#main
  section#top                 — первый экран
  section#questions           — раннее доказательство и вопросы
  section#system              — управленческий цикл
  section#results             — результат собственника
  section#cases               — кейсы и доказательства
  section#formats             — маршруты и стоимость
  section#about               — почему Ксения
  section#contact             — первый шаг, FAQ и финальный CTA
footer.site-footer

dialog#qualifier-dialog       — единый мини-бриф
optional dialog#evidence-dialog — просмотр реального доказательства
```

## 6.1. Заголовочная структура

- на странице ровно один `h1`;
- каждый крупный смысловой раздел имеет `h2`;
- вложенные смысловые единицы используют `h3`;
- уровни не перескакивают;
- декоративный текст не размечается заголовком только ради размера;
- все секции с `aria-labelledby` ссылаются на существующий заголовок.

## 6.2. Навигация

Десктоп:

- `Как работаю` → `#system`;
- `Кейсы` → `#cases`;
- `Форматы` → `#formats`;
- основная кнопка → квалификационный сценарий.

Мобильный экран:

- монограмма;
- короткое имя;
- компактная кнопка `Разобрать`;
- бургер-меню не создаётся.

## 6.3. Прогрессивное улучшение

Без JavaScript:

- весь основной контент читается;
- якорная навигация работает;
- FAQ работает на `<details>`;
- цикл виден в статичном состоянии;
- CTA ведёт к `#contact`;
- в `#contact` доступны прямые ссылки на MAX и e-mail;
- не показывается сломанная кнопка, зависящая только от JS.

С JavaScript CTA открывает единый мини-бриф.

# 7. Дизайн-система

## 7.1. Общий образ

> **Спокойная интеллектуальная уверенность.**

Сайт должен восприниматься как сайт финансового директора, который умеет разбираться в системе бизнеса, а не как:

- бухгалтерская фирма;
- интегратор 1С;
- инфобизнес;
- финтех-приложение;
- демонстрация визуальных эффектов;
- luxury-бренд без доказательств.

## 7.2. Базовая палитра

Сохранить исходные цвета прототипа как базовые токены:

```css
:root {
  color-scheme: light;

  --navy-950: #09132a;
  --navy-900: #0d1a36;
  --navy-850: #112142;
  --navy-800: #172b52;

  --cream: #f4f0e7;
  --paper: #fffaf1;
  --white: #ffffff;

  --gold: #b98330;
  --gold-dark: #765019;

  --ink-muted: #46516a;
  --line: rgba(13, 26, 54, 0.16);
  --line-strong: rgba(13, 26, 54, 0.28);
  --overlay: rgba(9, 19, 42, 0.68);

  --shadow-soft: 0 18px 50px rgba(9, 19, 42, 0.11);
  --shadow-button: 0 12px 28px rgba(13, 26, 54, 0.20);

  --radius-lg: 30px;
  --radius-md: 18px;
  --radius-sm: 12px;

  --container: 1300px;
  --header-height: 68px;
  --text-width: 66ch;
  --ease: cubic-bezier(0.2, 0.8, 0.2, 1);
}
```

Дополнительные токены допускаются только системно. Нельзя создавать для каждой секции случайные почти одинаковые оттенки.

## 7.3. Семантика цветов

Тёмно-синий:

- структура;
- профессиональная ответственность;
- основные кнопки;
- центральный раздел системы;
- финальный CTA.

Молочный и бумажный:

- основной фон;
- документы;
- доказательства;
- спокойные поверхности.

Золото:

- активный этап;
- выбранная связь;
- номер;
- направление действия;
- короткий акцент.

Золото нельзя использовать:

- для длинных абзацев;
- как фон больших карточек;
- для декоративного свечения по всей странице;
- как имитацию роскоши;
- вместо достаточного контраста.

## 7.4. Типографика

Использовать системные шрифты без внешней загрузки.

Заголовки:

```css
font-family: Georgia, "Times New Roman", serif;
```

Основной текст:

```css
font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", Arial, sans-serif;
```

Ориентиры:

- `h1`: `clamp(2.35rem, 4.15vw, 4.5rem)`;
- `h2`: `clamp(2.1rem, 3.4vw, 3.8rem)`;
- `h3`: `clamp(1.35rem, 1.4vw, 1.8rem)`;
- основной текст: 16–20 px в зависимости от роли;
- вспомогательный текст: не менее 14 px;
- межстрочный интервал основного текста: 1.45–1.6;
- длина строки: до 60–66 знаков;
- `hyphens: none` для ключевых заголовков;
- `text-wrap: balance` используется как прогрессивное улучшение;
- русские слова в H1 не должны переноситься по частям.

Не подключать декоративные шрифты, которые меняют утверждённый характер первого экрана.

## 7.5. Отступы и ритм

Использовать единую шкалу, например:

```css
--space-1: 0.25rem;
--space-2: 0.5rem;
--space-3: 0.75rem;
--space-4: 1rem;
--space-5: 1.5rem;
--space-6: 2rem;
--space-7: 3rem;
--space-8: 4rem;
--space-9: 6rem;
--section-space: clamp(4.5rem, 8vw, 8.5rem);
```

Не добавлять локальные случайные отступы, если значение уже покрывается шкалой.

## 7.6. Кнопки и ссылки

Основная кнопка на светлом фоне:

- тёмно-синяя заливка;
- белый текст;
- овальная или сильно скруглённая форма;
- высота не менее 52–54 px;
- спокойный hover без яркого свечения;
- видимый `focus-visible`;
- состояние active без скачка макета.

Основная кнопка на тёмном фоне:

- светлая заливка;
- тёмно-синий текст;
- тот же размер и радиус.

Текстовые ссылки:

- визуально распознаются как ссылки;
- имеют hover и focus;
- не конкурируют с заполненным CTA.

Все внешние ссылки, открывающиеся в новой вкладке:

```html
rel="noopener noreferrer"
```

## 7.7. Поверхности

- без тяжёлого glassmorphism;
- без множества теней;
- без одинаковых карточек для каждого абзаца;
- тонкие линии, бумажные поверхности, редакционные списки;
- главный кейс и основная услуга визуально доминируют;
- второй кейс и дополнительные маршруты подчинены.

### Врезка

> **Налоговый и управленческий учёт могут использовать часть одних и тех же исходных данных, но отвечают на разные вопросы. Налоговая база не заменяет управленческую экономику товара, канала или решения.**

### Обязательные правила SVG

- SVG используется только как визуальное пояснение; полный смысл продублирован в HTML;
- SVG имеет `aria-hidden="true"`, если все подписи повторены рядом;
- не более 12–14 одновременно видимых коротких подписей;
- общий образ — замкнутый контур, не спираль роста;
- этапы соединены направленным циклом;
- активный этап — золотой акцент;
- неактивные этапы остаются видимыми;
- никаких графиков постоянного роста;
- никаких процентов;
- никаких вымышленных финансовых показателей;
- SVG должен масштабироваться без горизонтальной прокрутки.

### Поведение на десктопе

- двухколоночная секция;
- слева или справа — четыре текстовых этапа;
- визуальная схема может быть `position: sticky`, но без блокировки скролла;
- `IntersectionObserver` меняет активный этап по мере обычной прокрутки;
- не применять scroll-jacking.

### Поведение на мобильном

- сложный SVG скрывается;
- показываются четыре последовательных смысловых блока;
- каждый блок содержит номер, заголовок, короткий текст и упрощённый декоративный знак;
- нет фиксированной высоты;
- нет sticky-сцены.

### `prefers-reduced-motion`

- движение сигнала отключено;
- переходы почти мгновенные;
- все четыре этапа видимы в статичном полном состоянии;
- понимание схемы не зависит от анимации.

## 8.5. Раздел 4 — результат собственника `#results`

### Надзаголовок

> **Результат для собственника**

### H2

> **Не больше отчётов — меньше неопределённости перед решением**

### Основной текст

> **Финансовая система ценна не количеством форм. Она создаёт согласованную основу, на которой собственник может понять причины результата, сравнить действия и проверить последствия.**

### Пять результатов

#### Одна согласованная картина

> Прибыль, деньги, запасы, расчёты и обязательства рассматриваются совместно, а не в отдельных версиях файлов.

#### Понимание причин

> Видно не только отклонение показателя, но и операционный или финансовый механизм, который его сформировал.

#### Сценарий до действия

> Можно сравнить варианты по влиянию на прибыль, деньги, обязательства и требуемый ресурс.

#### Проверка после действия

> План сопоставляется с фактом, а вывод используется в следующем управленческом цикле.

#### Снижение ручной зависимости

> Повторяемая часть меньше зависит от памяти сотрудника, отдельного файла и ежемесячной ручной последовательности.

### Сравнение

| Этап | Когда данные собираются вручную | Когда финансовый цикл работает регулярно |
|---|---|---|
| До решения | Собственник выясняет, какой версии цифр доверять | Получает согласованную картину по установленным правилам |
| В момент решения | Ориентируется на общий итог, остаток на счёте и интуицию | Сравнивает варианты по нескольким связанным показателям |
| После решения | Узнаёт о последствиях, когда они уже проявились | Сопоставляет ожидаемый и фактический результат |

### Вывод

> **Собственник перестаёт быть сборщиком цифр и возвращается к своей управленческой роли: формулировать вопрос, выбирать действие и контролировать результат.**

### Интерфейсные требования

- пять результатов не оформлять пятью одинаковыми громоздкими карточками;
- использовать нумерованный список, колонки или компактные бумажные панели;
- сравнение остаётся семантической таблицей;
- на мобильном строки таблицы перестраиваются вертикально без горизонтального скролла;
- заголовки колонок сохраняются доступными для экранных дикторов;
- не дублировать ту же таблицу отдельной мобильной копией в DOM.

На странице существует только один экземпляр формы. Все CTA используют ссылку вида:

```html
<a href="#contact" data-open-qualifier data-cta-location="hero">
```

При наличии JavaScript:

- предотвращается переход по якорю;
- открывается `dialog#qualifier-dialog`;
- фокус переводится на заголовок либо первое поле;
- источник CTA сохраняется только как безопасный технический параметр.

Без JavaScript:

- ссылка ведёт к `#contact`;
- там доступны MAX и e-mail;
- страница остаётся функциональной.

- введённые данные не удаляются при ошибке;

## 9.9. Работа с MAX

Точная возможность предварительного заполнения текста в MAX должна быть проверена отдельно после получения реальной ссылки.

Логика должна поддерживать два режима.

### Режим A — предварительное заполнение поддерживается

Если заполнен `maxPrefillUrlTemplate`, сформировать URL только через `encodeURIComponent(message)` и показать пользователю явную кнопку перехода.

Нельзя конкатенировать необработанный пользовательский текст в URL.

### Режим B — предварительное заполнение не поддерживается

1. Сформировать текст.
2. Попытаться скопировать его через Clipboard API.
3. При отсутствии secure context или ошибке использовать безопасный fallback с временным `textarea` и выбором текста.
4. Переключить диалог на экран подтверждения.
5. Показать:

```text
Текст сообщения подготовлен и скопирован. Откройте MAX и вставьте его в чат.
```

6. Показать кнопку:

```text
Открыть MAX
```

7. Показать действие:

```text
Скопировать ещё раз
```

Не открывать внешнее приложение до того, как пользователь увидел результат копирования.

## 9.10. Работа с e-mail

`mailto:` должен формироваться через `URLSearchParams` либо корректное кодирование:

- адрес — из `SITE_CONFIG.email`;
- тема — `Разбор финансовой ситуации — сайт`;
- тело — сформированное сообщение, если форма заполнена;
- внешнее значение не вставляется как HTML.

## 9.11. Жизненный цикл диалога

- открытие по любому CTA;
- закрытие по кнопке;
- закрытие по Escape;
- закрытие по клику на backdrop допустимо;
- при закрытии фокус возвращается на CTA, который открыл диалог;
- при повторном открытии введённые данные в рамках текущей страницы сохраняются в DOM;
- после успешного перехода форму не очищать автоматически до перезагрузки;
- данные не записывать в `localStorage`, cookies или аналитику;
- если `dialog.showModal()` не поддерживается, не ломать якорный fallback.

## 9.12. Безопасный DOM

Запрещено:

```js
container.innerHTML = userValue;
```

Использовать:

- `textContent`;
- `setAttribute` только после проверки значения;
- `URL` и `URLSearchParams`;
- заранее созданные DOM-узлы.

# 11. Событийная аналитика

## 11.1. Архитектура адаптера

Создать `assets/js/analytics.js` с единым публичным интерфейсом:

```js
window.siteAnalytics = Object.freeze({
  track(eventName, params = {}) {
    // no-op при отключённой аналитике
  }
});
```

Основной код сайта не должен обращаться напрямую к глобальной функции конкретного поставщика.

Провайдер подключается только внутри адаптера после отдельного решения Ксении.

## 11.2. Режимы

```text
disabled   — никаких сетевых запросов;
cookieless — только если выбранный сервис и юридическая схема это подтверждают;
consent    — события после согласия пользователя.
```

По умолчанию разработка работает в режиме `disabled`.

## 11.3. Обязательные события

| Событие | Триггер | Разрешённые параметры |
|---|---|---|
| `hero_cta_click` | клик по CTA первого экрана | `cta_location: "hero"` |
| `qualifier_open` | успешное открытие мини-брифа | `cta_location` |
| `qualifier_start` | первое изменение любого поля, один раз за загрузку | `cta_location` |
| `qualifier_complete` | обязательные поля прошли валидацию | `cta_location`, `has_optional_scale`, `has_optional_deadline`, `has_utm` |
| `max_continue_click` | явный клик по кнопке открытия MAX | `prefill_mode`, `copy_status`, `cta_location` |

Никогда не передавать:

- содержание полей;

- e-mail пользователя;
- телефон;
- текст сообщения;

- название загруженного файла, поскольку загрузки файлов отсутствуют.

## 11.5. События просмотра

Для `case_main_view` и `pricing_view` использовать `IntersectionObserver`.

- событие отправляется один раз за загрузку страницы;
- ориентир порога — 40–50% видимого блока;
- событие не отправляется при программном создании скрытого блока;
- отсутствие `IntersectionObserver` не ломает страницу;
- не использовать тяжёлый scroll listener.

# 12. Безопасность и конфиденциальность

## 12.1. CSP

В development при отключённой аналитике допустима строгая политика:

```text
default-src 'self';
img-src 'self' data:;
style-src 'self';
script-src 'self';
connect-src 'none';
media-src 'self';
object-src 'none';
base-uri 'none';
form-action 'none';
frame-ancestors 'none';
```

После выбора аналитики:

- добавить только точные необходимые домены в `script-src`, `connect-src` и при необходимости `img-src`;
- не использовать `*`;
- не возвращать `unsafe-inline`, если можно использовать внешние файлы;
- если требуется inline JSON-LD, использовать хеш/nonce или иной точечный механизм, а не ослаблять всю политику;
- предпочтительно задавать CSP HTTP-заголовком хостинга; meta допускается как fallback, если хостинг не позволяет настроить заголовки.

## 12.2. Дополнительные заголовки

Подготовить рекомендации для хостинга:

```text
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()
Content-Security-Policy: ...
```

`frame-ancestors` задаётся через CSP-заголовок.

Не заявлять, что заголовки включены, пока они не проверены на реальном домене.

## 12.3. Формы

- нет серверной отправки;
- нет endpoint;
- нет скрытых AJAX-запросов;
- нет стороннего form service;
- нет file upload;
- значения существуют только в памяти вкладки;
- form submit всегда перехватывается безопасно;
- при отключённом JS форма не должна отправляться методом GET и помещать текст в URL;
- форма без JS может быть скрыта, но рядом обязательны прямые контакты.

## 12.4. Внешние ссылки

- MAX и e-mail берутся из конфигурации;
- URL MAX проверяется через `new URL()`;
- разрешаются только `https:` и явно согласованные deep-link схемы;
- `javascript:` и `data:` запрещены;
- внешняя вкладка использует `noopener noreferrer`;
- пользовательский текст кодируется.

## 12.5. Клиентские доказательства

- обезличивание выполняется в самом экспортированном файле;
- CSS-blur не считается обезличиванием;
- скрытый слой исходного документа не должен содержать конфиденциальные данные;
- исходники клиента не помещаются в публичный репозиторий;
- в репозиторий добавляются только утверждённые публичные копии;
- имена файлов не содержат имя клиента, ИНН или коммерческую тайну.

## 13.1. Общие требования

- skip-link `К содержанию` сохраняется;

- `aria-labelledby` указывает на заголовок;

## 13.4. Видео

- подпись объясняет статус ролика;
- автозвук запрещён;
- отсутствие видео не блокирует понимание компетенций.

## 13.5. FAQ

- использовать `<details>/<summary>`;
- summary имеет видимый фокус;
- иконка раскрытия декоративна;

# 19. Технический долг текущего прототипа

Codex должен учитывать следующие известные особенности исходного `index(2).html`:

1. В `<head>` установлен `noindex, nofollow`; он сохраняется до Этапа 9.
2. CSP содержит `connect-src 'none'`; это совместимо с отключённой аналитикой, но не с реальным счётчиком.
3. CSS и JS встроены в HTML.
4. Несколько ключевых селекторов hero повторно переопределяются в конце `<style>`.
5. CTA ведёт в модальное окно-заглушку.
6. В тексте заглушки сказано, что канал будет подключён позже.
7. `alt` портрета пустой.
8. Метаданные отражают старую иерархию, где автоматизация стоит раньше роли CFO.
9. Ниже первого экрана отсутствуют остальные блоки v5.0.
10. HTML ссылается на локальные изображения; их фактическое наличие в репозитории нужно проверить.

## 19.1. Обязательное правило рефакторинга

Не добавлять новые стили в конец текущего CSS как ещё один слой исправлений.

Нужно:

- определить итоговые значения;
- удалить устаревшие дубли;
- объединить media queries;
- сгруппировать CSS по компонентам;
- сохранить визуальный baseline;
- после рефакторинга проверить первый экран на всех контрольных размерах.

# 24. Автоматическая предпубликационная проверка

Codex должен добавить небольшой скрипт на стандартном Node.js без сторонних пакетов либо эквивалентную проверку средствами репозитория.

Минимально проверять:

- наличие `index.html`;
- отсутствие `{{...}}` в production-файлах;
- отсутствие `TODO`, `REPLACE_BEFORE_PUBLISH`;
- отсутствие текста «канал записи будет подключён»;
- отсутствие пустого `alt` у портрета;
- наличие ровно одного `<h1`;
- отсутствие `noindex` только в production-режиме финального release;
- наличие `privacy.html`, `robots.txt`, `sitemap.xml`;
- наличие файлов, указанных в локальных `src`, `srcset`, `poster`;
- отсутствие `http://` в production-разметке;
- отсутствие известных спорных числовых формулировок;
- отсутствие inline event handlers (`onclick=`, `oninput=`);
- отсутствие `javascript:` URL.

Скрипт не заменяет ручной QA и не должен заявлять полную HTML-валидацию, если её фактически не выполняет.

# 27. Итоговая формула реализации

Codex должен построить не просто длинную страницу и не демонстрацию автоматизации.

Итоговый пользовательский маршрут:

> **Понять роль финансового директора → узнать свой вопрос → увидеть ранний факт проекта → понять работу финансовой системы → увидеть управленческий результат и доказательства → определить возможный маршрут и стоимость → пройти короткую квалификацию → перейти к содержательному обращению.**

Итоговая техническая логика:

> **Семантический статический сайт → progressive enhancement → единый мини-бриф без серверной передачи → безопасный переход в MAX/e-mail → событийная аналитика без содержимого полей → строгая публикационная проверка.**

Любое изменение, которое делает интерфейс эффектнее, но ослабляет эту коммерческую, методологическую или доказательную последовательность, не принимается.
